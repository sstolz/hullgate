# BR-060 · No code without the operator at the barrier or on the host

## Rule

The authorization server issues a code, whatever the client's admission mode, only after a valid TOTP code (RFC 6238) of the operator, never twice the code of the same time step, or a passkey assertion of an active administrator under the conditions of BR-202, entered on the barrier page, or the operator's approval of that one pending request from the host (BR-310); with neither a TOTP secret configured nor a passkey usable at this origin, every authorisation is refused at `/authorize`, after checking the client and the `redirect_uri`: `access_denied` by redirect to a checked `redirect_uri`, an error page otherwise (same form as BR-058).

## Clarifications

- Spec lines 773-774: authentication of the administrator on the consent page by passkey or TOTP. The TOTP factor uses a 30 s step, 6 digits and ±1 step tolerance; F-016 adds the passkey factor.
- The TOTP secret is a mounted secret (BR-032 v2, `AUTHORIZE_TOTP_SECRET_FILE`), enrolled by the operator in their authenticator application (runbook); neither it nor a code appears in a response, a log or an audit entry.
- A pending request is identified by a random value of at least 192 bits (256 in v1, the database keeps only its fingerprint), single-use, and expires in 10 min; a failed code does not consume it; a denial ("Deny", which redirects `access_denied`) and a success consume it.
- A wrong code, one outside the tolerance or from a step already accepted redisplays the page (200, generic message) and counts as a failure (BR-073).
- The last accepted time step is kept in the database (it survives a restart, like the counter of BR-073): a code is refused if the step it validates is lower than or equal to that one. Six digits legitimately repeat at another step: only repetition within the same step is forbidden.
- The page shows the client and the path of the requested role; "Deny" redirects `access_denied`. Responses carry `Cache-Control: no-store`, `Content-Security-Policy: frame-ancestors 'none'`.
- Attempt limit: BR-073 (spec lines 342, 983-985). The specification describes a consent page that also offers levels below the role (connection + mode, spec lines 419-420): in F-005 it offers only the role.
- The barrier offers the passkey only when the host of `PUBLIC_URL` is `ADMIN_RP_ID` or a subdomain of it. Under `localhost` it stays TOTP only.
- The audit records which factor passed.
- The barrier's origin is `PUBLIC_URL`'s; BR-202's origin check reads it for this page.
- This is no weaker a proof than the barrier's factors: it requires the host, which holds the TOTP secret.
- With neither a TOTP secret nor a usable passkey, `/authorize` still refuses, so no request is pending to approve. Unchanged in 1.0.0.
