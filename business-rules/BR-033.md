# BR-033 · /healthz and /readyz probes without authentication

## Rule

The public listener serves `GET /healthz` (200 as long as the process responds) and `GET /readyz` (200 if the database in `DATA_DIR` is open, accepts a write lock, is at the code's schema, and if the signing key is available in the sense of BR-064: file readable and parseable; 503 otherwise), without authentication; the admin listener serves `GET /healthz`. A gap fails the integration test.

## Clarifications

- Writability is checked without writing: `BEGIN IMMEDIATE` then `ROLLBACK`, wait timeout bounded to 1 s. In WAL mode the write lock lives in `-shm` and is obtained even on a read-only file: the right to write the file is checked separately (`os.access`, reason `db_read_only`); a file deleted after opening gives `db_unavailable`.
- Response bodies: JSON `{"status": "ok"}` or `{"status": "unavailable", "reason": "<code>"}`; no file path or exception message in the body.
- Database missing at startup: created empty; opening impossible: the process starts anyway, `/healthz` 200 and `/readyz` 503 (SCR-02.db-unavailable).
- Reasons added in v2: `key_unavailable`, `schema_error`, `schema_too_new` (BR-069).
- Signing key: file at `SIGNING_KEY_FILE` readable and a valid EC P-256 key, re-read on every request; reason `key_unavailable`, evaluated after the database ones.
