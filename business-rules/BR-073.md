# BR-073 · The TOTP barrier closes after five failures in fifteen minutes

## Rule

While the barrier counts 5 wrong codes or more in the last 15 minutes (sliding window), it refuses any TOTP entry without evaluating it, with a generic message and a 429 status, and issues no code by that factor; a passkey assertion stays evaluated.

## Clarifications

- Global window, not per address (H10): a third party can close the TOTP entry as long as it renews its failures (risk §12); it can neither obtain a code nor touch existing tokens.
- Every failure and every refusal due to closure is audited (`consent_failed`, `consent_locked`).
- The counter is in the database (it survives a restart).
- A failed passkey assertion falls under BR-207, not under this window. A third party can therefore no longer block authorisation when a passkey is usable at this origin (F-005 §12 risk lifted in that configuration only).
- F-020: the check of the window, the evaluation of the code and the count of a failure run in one write transaction, so that parallel entries cannot pass the check together, and that transaction purges rows past the window. The lockout stands for TOTP, and BR-310 is what lifts it for the operator.
