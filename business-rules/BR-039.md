# BR-039 · A backup is checked by restoring it, without touching production

## Rule

`make restore-check` proves that a backup (the most recent by default) restarts the gateway, in a disposable volume and container, without stopping or modifying the service and its database; a failing check exits ≠ 0 naming the step. The comparison is made on the restored copy **after** the current code's migrations are applied (`backup restore` counts after migration), so that a backup older than the current schema passes; the printed line is `RESTORE-CHECK: OK <fichier> readyz=200 connections=<n> (key_absent) tables={…}`.

## Clarifications

- The backup enters through the standard input of a disposable container (`python -m hullgate.backup restore -`), checked under a working name before being put in place: no host mount.
- `restore-check` starts without a connections key (F-006): when the backed-up database carries connections, the restore is proven with those connections seen as `key_absent` (BR-088) and the same number of rows per table (`RESTORE-CHECK: OK … connections=<n> (key_absent)`). No disposable connections key is provided: it would create the "key_different" case on a copy of the production database without proving anything more.
