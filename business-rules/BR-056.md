# BR-056 · Each access point has its own, discoverable authorization server

## Rule

Each access point publishes its RFC 9728 metadata (its own URL as `resource`, its own issuer `${PUBLIC_URL}/o/<id>/oauth/p/<path>` as `authorization_servers`, spec lines 749-753) and its authorization server publishes its RFC 8414 metadata under that issuer; a code, an access token or a renewal issued by an access point's authorization server is refused by the access point (BR-055, step 6) or by the authorization server (code, renewal) of any other access point.

## Clarifications

- `code_challenge_methods_supported` = [`S256`]; `scopes_supported` = [`mcp`] on the resource side, [`mcp`, `offline_access`] on the authorization server side (values of the POCs' operator walkthrough, `docs/trials/poc-python.md` "Operator step"; `offline_access` is only announced, a renewal is issued at every authorization, BR-059); `token_endpoint_auth_methods_supported` = [`none`] (public clients only, BR-061); `registration_endpoint` present if and only if DCR is active (BR-061).
- The published URLs derive from `PUBLIC_URL`, never from the `Host` header.
- The root `/.well-known/oauth-protected-resource` (without a path) answers 404.
- Metadata locations follow the scheme of F-014 §3.1: `/.well-known/oauth-protected-resource/o/<id>/p/<path>/mcp` and `/.well-known/oauth-authorization-server/o/<id>/oauth/p/<path>`; `<id>` is the organisation's public identifier (BR-160).
