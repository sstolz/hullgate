# BR-112 · Upstream definitions are cached per (role, connection) and are never an authorization

## Rule

The tool definition cache is keyed by (role, connection), never shared between roles, lives at most 300 s, and is discarded as soon as the placement, the effective sensitivity (BR-186), the state or the URL of the connection read from the database at the request differ from those of its filling, or the role has gone; the authorisation of a call is read again from the database at each request and is never deduced from a cache entry; the policy state (BR-123) is read at each request, never cached, list included.

## Clarifications

- One upstream fetch at a time per key: concurrent requests on a cold key wait for the same one (no burst toward the upstream).
- The CLI is another process than the server: no invalidation goes by message. At each request served and for **all** its keys (not only the request's), the server compares what it reads from the database with the fingerprint of the filling; `connection tools` always reads afresh, outside the cache, and has no refresh option (H20).
- Toward the upstream, no `list_changed` notification is listened to in v1 (no GET stream); the 300 s delay and the invalidations above stand in for it (H13).
- A warm cache does not bring back the tools of a connection whose placement has just been removed: the list first rebuilds the set of authorised connections from the database.
- A policy change (mode, list, argument rule, classification) applies at the next request, warm cache included, with no restart: the role's policy state is loaded once per request, not per tool (F-015).
