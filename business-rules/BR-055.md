# BR-055 · The authorization order at the access point is fixed and closed by default

## Rule

A request to a role's access point goes through, in this order, (1) path of an existing role under the instance's own organisation identifier (BR-161), otherwise 404; (2) vault and key available in the sense of BR-064, otherwise 503; (3) token present, otherwise 401 with `WWW-Authenticate: Bearer resource_metadata="<métadonnées RFC 9728 de ce point d'accès>"`; (4) token well formed and authentic (known unexpired operator token, or JWT conforming to BR-054 and unexpired), otherwise 401 `invalid_token`; (5) token neither revoked nor attached to a deleted node, otherwise 401 `invalid_token`; (6) for an OAuth token, audience exactly equal to the called access point's URL, then for any token, path a segment-wise prefix of the role's (BR-050) and no sensitive environment crossed by a token issued above the role (BR-051), otherwise 401 `invalid_token`; (7) scope `mcp` (N2), otherwise 403 `insufficient_scope`; the first failing step answers and no following step nor MCP processing takes place.

## Clarifications

- Each refusal (steps 3 to 7) is audited with a distinct reason (`missing_token`, `invalid_token`, `revoked`, `node_deleted`, `audience_mismatch`, `out_of_scope`, `sensitive_requires_role_token`, `insufficient_scope`); the HTTP response does not distinguish the reasons of steps 4 to 6 beyond the RFC 6750 code. At step 6, an audience different from the access point's URL is `audience_mismatch` and an uncovered path `out_of_scope` (batch B, where a real token's audience appears for the first time, separates the two reasons that batch A conflated).
- Step 1 before authentication: a nonexistent URL answers 404 even without a token (H13, existence of a path revealed, risk accepted §12; T14 expects the root to give 404).
- The state (revocation, node, sensitivity) is read on every request, without cache: a revocation or deletion takes effect from the next request.
- Operator tokens implicitly carry the scope `mcp`.
- Correspondence with the specification (spec lines 376-400): its steps 1 (validity: signature, issuer, expiry, revocation, type), 2 (single audience), 3 (segment-wise prefix), 4 (sensitive) = steps 4 to 6 here; its steps 5 (effective rights = URL ∩ token ∩ policy) and 6 (connection placed in this role) belong to #10 and #9. The specification requires an audience equal to the access point for any token; a path token (`mpx/cairn`, spec line 363) covers several access points and cannot have a single one: the core applies the audience to OAuth tokens and the path prefix to all (reading confirmed at the freeze by the operator, option 1).
- The two token families plug in at step 4 through resolvers (operator token by its fingerprint, OAuth JWT by signature then the registry of `jti`); step 2 reads the vault then the key (delivered in two batches, §10).
- If the database cannot be read for step 1, the response is 503 (BR-064), never a 404 caused by the failure.
- Step 1 reads the whole path (F-014): the instance's identifier (BR-160, BR-161) and an existing role, in one read of the store; a foreign well-formed identifier answers exactly as an unknown role. Access points read `/o/<id>/p/<client>/<project>/<env>/<role>/mcp`.
