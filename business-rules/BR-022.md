# BR-022 · The inbound token never crosses to the upstream

## Rule

The requests the gateway sends to the upstream carry only the token of the role's connection; the access or renewal token received from the client is never forwarded, neither in a header, nor in a parameter, nor in a body; a fingerprint of an inbound token in an upstream log is a failure of the gateway, reported as an isolation gap.

## Clarifications

- Positive check: the upstream does receive the connection token's fingerprint for the authorized call (T01).
- The received fingerprint is an addition to the log of `upstream/server.py` (BR-013); it is read on the bench upstream. On the Gitea path, it is read on the front if the connection token goes through the request (`-oauth` mode); if it is fixed at startup of the Gitea MCP server, the front must receive no `Authorization` coming from the gateway.
- Since F-008 the relay exists and the check is played against v1 (BR-114): the only secret presented to the upstream is the one `get_access(connexion, rôle)` returns, and no fingerprint of a token issued to a client appears in the union of the upstream logs; the bench replays the check against the real `gitea-mcp` (run `--target v1`, `BR-015/BR-022` and `BR-022`).
